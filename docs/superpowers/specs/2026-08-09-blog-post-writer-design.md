# 블로그 글 작성 스킬 설계

## 목적과 범위

`namonak.dev`에서 새로 작성하는 개발자 대상 블로그 글을 위한 저장소 전용 Codex 스킬을 만든다.
스킬은 주제 기반 글과 외부 아티클 기반 글 모두에 적용한다.

레거시 WordPress 글의 이전은 이 스킬의 대상이 아니다.
`docs/superpowers/plans/2026-08-09-legacy-article-migration.md`의 절차를 그대로 따른다.

## 배치와 활성화

다음 파일을 저장소에서 버전 관리한다.

```text
skills/
  blog-post-writer/
    SKILL.md
    references/
      voice-and-structure.md
      evidence-and-citations.md
      quality-gates.md
```

- `SKILL.md`는 적용 범위, 작업 순서, 입력 판단과 실패 처리를 정의한다.
- `voice-and-structure.md`는 기존 글에서 확인한 문체와 글의 전개 방식을 정의한다.
- `evidence-and-citations.md`는 조사, 출처 선택, 아티클 검증, 인용 형식을 정의한다.
- `quality-gates.md`는 Astro 콘텐츠 규칙과 검증·인계 절차를 정의한다.
- 루트 `AGENTS.md`는 새 원본 블로그 글을 작성·요약·갱신할 때 이 스킬을 먼저 읽도록 지시한다.

이 방식은 이 저장소에서 실행하는 Codex에 확실히 적용된다.
임의의 저장소 경로에 둔 `SKILL.md`가 전역 `$스킬명`으로 자동 발견되는 방식은 아니다.
전역 호출이나 배포가 필요해질 때만 Codex 플러그인화를 별도 작업으로 검토한다.

## 스킬 문서 언어

`SKILL.md`와 모든 보조 문서는 반드시 한국어로 작성한다.
파일 경로, 명령어, 코드, 제품명, 인용한 원문 제목처럼 번역하면 정확성이 떨어지는 식별자는 원문을 유지한다.
스킬이 사용자에게 출력하는 진행 안내와 확인 결과도 한국어로 쓴다.

## 독자와 판단 기준

독자는 개발자로 고정한다.
스킬은 사용자가 별도로 정하지 않아도 주제 또는 원문에서 글의 범위, 기존 카테고리, 경로 안전한 슬러그를 우선 판단한다.
사용자 지정은 항상 우선한다.

다음 경우에만 글의 방향을 바꿀 수 있는 한 가지 질문을 한다.

- 서로 다른 기술 또는 문제를 다루는 넓은 주제라서 글의 범위를 합리적으로 하나로 좁힐 수 없는 경우
- 지원하는 버전, 플랫폼, 독자 수준이 결론을 달리하게 만드는 경우
- 원문·공식 문서·표준 사이의 충돌을 추가 맥락 없이 해소할 수 없는 경우

## 조사와 근거

모든 글은 작성 전에 조사를 마친다.

1. 입력을 주제 기반 또는 아티클 기반으로 분류한다.
2. 개발자가 글을 읽고 이해·판단·적용할 수 있어야 하는 범위를 한 문장으로 정한다.
3. 글의 핵심 주장, 수치, 인용, 버전 의존 설명을 목록화한다.
4. 각 항목을 공식 문서, 표준, 원 논문, 공식 API 문서 같은 1차 출처로 우선 검증한다.
5. 근거가 부족한 주장은 제거하거나 불확실성과 적용 조건을 명시한다.

아티클 기반 글은 원문을 출발점으로만 삼는다.
원문의 주장과 확인한 근거가 다르면, 원문의 맥락 또는 버전을 밝힌 뒤 검증한 근거를 기준으로 설명한다.
원문을 장문으로 인용하거나 단순 재서술하지 않는다.

실무 경험과 작성자의 판단은 외부 사실과 분리한다.
경험을 일반화하지 않고 재현 조건이나 한계를 함께 쓴다.

## 출처 형식

외부의 검증 가능한 기술 주장에는 GFM 각주를 사용한다.

```md
CORS는 동일 출처 정책과 함께 이해해야 합니다.[^mdn-cors]

[^mdn-cors]: [MDN: Cross-Origin Resource Sharing](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)
```

- 식별자는 `[^mdn-cors]`처럼 의미 있게 쓴다.
- 독자에게 보이는 번호, 각주 이동, 본문 복귀 링크는 `remark-gfm` 렌더러가 자동 생성한다.
- 수동 번호, `## 참고` 목록, HTML 앵커는 사용하지 않는다.

아티클 기반 글은 frontmatter 바로 다음에 원문을 보이는 링크로 표기한다.

```md
> 원문: [Kotlin library useful functions](https://medium.com/@KaushalVasava/kotlin-library-useful-functions-4a85e182fd1b)
```

이 표기는 글의 출발점을 밝히는 용도다.
사실 검증을 위한 독립적인 각주를 대체하지 않는다.

## 글의 구성과 문체

기본 전개는 `정의 → 원리 → 코드·예시 → 적용 또는 주의점 → 정리`다.
주제에 따라 불필요한 단계를 빼거나 비교표·Mermaid를 추가할 수 있다.

- 도입부는 2~4문장으로 개념과 독자가 얻게 될 결과를 제시한다.
- 제목과 `description`은 개발자가 검색 결과에서 문제와 범위를 이해할 수 있게 쓴다.
- 본문은 자연스러운 한국어 존댓말로 쓴다.
- 검증된 사실은 “이때 … 합니다”, “이 메서드는 … 을 반환합니다”처럼 명료하게 설명한다.
- 버전·환경·설정에 따라 달라지는 내용은 적용 조건을 먼저 밝히고 절대적으로 단정하지 않는다.
- 어려운 핵심 개념에는 정확한 정의와 원리를 먼저 쓴 뒤, 이해를 돕는 짧은 비유를 보조적으로 쓴다.
- 비유는 서론 장식이나 정확한 설명의 대체물이 아니며, 기본 글 구조를 바꾸지 않는다.
- 코드 블록에는 언어 식별자를 지정한다.

## 초안, 검증, 인계

스킬은 `src/content/blog/<category>/<slug>.md`에 새 파일을 만들고 `draft: true`를 명시한다.
기존 공개 URL 또는 파일과 충돌하면 덮어쓰지 않고 다른 적절한 슬러그를 선택한다.

작성 전에는 `ARCHITECTURE.md`, `docs/content-guide.md`, 콘텐츠 컬렉션 스키마와 기존 카테고리를 확인한다.
새 글은 해당 문서가 정한 frontmatter, 이미지, Mermaid, 공개 URL 규칙을 따라야 한다.

초안 후에는 다음을 수행한다.

1. frontmatter, 파일 경로, GFM 각주, 코드 언어, 이미지 경로, Mermaid 문법을 점검한다.
2. `npm run check`, `npm run test`, `npm run build`를 실행한다.
3. Mermaid가 있으면 `npm run validate:mermaid`를 실행한다.
4. 로컬 렌더링에서 데스크톱, 태블릿, 모바일 폭의 본문·코드·표·이미지·Mermaid·각주 이동과 복귀를 확인한다.
5. 가능한 코드 예시는 실행하거나 프로젝트의 검증 도구로 확인한다. 실행하지 못한 예시의 결과는 사실처럼 단정하지 않는다.

검증 실패는 수정한 뒤 같은 게이트를 다시 통과해야 한다.
초안 인계에는 파일 경로, 실행한 검사 결과, 주요 출처, 남은 확인 사항만 간결하게 적는다.
스킬은 사용자의 명시적 지시 없이 `draft`를 해제하거나, 커밋하거나, 푸시하지 않는다.

## 검증 가능성

구현 후에는 다음을 확인한다.

- `AGENTS.md`의 지시를 따라 새 원본 글 작업에서 스킬을 읽을 수 있다.
- 주제 기반과 아티클 기반 입력 각각에서 조사·출처 확인이 초안보다 먼저 수행된다.
- 아티클 기반 초안은 보이는 `> 원문:` 블록과 독립적인 GFM 각주를 함께 가진다.
- 초안은 항상 `draft: true`이며, 콘텐츠 검증과 사이트 빌드를 통과한다.
- HTML 앵커나 수동 `## 참고` 목록 없이 GFM 각주가 렌더링되고 본문 복귀 링크를 제공한다.
