# 블로그 글 작성 스킬

신규 개발자 대상 블로그 글을 조사·검증한 뒤, 이 저장소의 비공개 Markdown 초안으로 작성할 때 사용합니다.

## 적용 대상과 제외 대상

- 사용자가 기술 주제를 제시한 경우와 외부 아티클을 바탕으로 글을 요청한 경우에 적용합니다.
- 레거시 WordPress 글의 마이그레이션에는 적용하지 않습니다. 해당 작업은 `docs/superpowers/plans/2026-08-09-legacy-article-migration.md`의 절차를 따릅니다.
- 독자는 개발자로 고정합니다. 특정 언어·플랫폼 경험이 없는 독자를 전제로 과도하게 풀어 쓰지 않습니다.

## 시작 전 필수 읽기

다음 파일을 읽고 현재 사이트의 콘텐츠 계약을 확인합니다.

1. `ARCHITECTURE.md`
2. `docs/content-guide.md`
3. `src/content.config.ts`
4. `src/content/blog/`의 기존 카테고리와 공개 경로
5. [문체와 글 구성](references/voice-and-structure.md)
6. [근거와 인용](references/evidence-and-citations.md)
7. [품질 게이트](references/quality-gates.md)

## 입력 판단과 질문 기준

입력을 주제 기반 글 또는 아티클 기반 글로 분류합니다.
글의 범위, 기존 카테고리, 경로 안전한 슬러그는 우선 판단합니다. 사용자가 지정한 값은 항상 우선합니다.

다음처럼 결론이나 글의 성격이 달라지는 경우에만 한 가지 질문을 합니다.

- 서로 다른 기술 또는 문제를 다루는 넓은 주제를 하나의 글로 합리적으로 좁힐 수 없는 경우
- 지원 버전, 플랫폼, 독자 수준이 기술적 결론을 바꾸는 경우
- 원문, 공식 문서, 표준의 충돌을 추가 맥락 없이 해소할 수 없는 경우

## 조사와 근거 확인

글을 쓰기 전에 개발자가 글을 읽고 이해·판단·적용할 수 있어야 하는 범위를 한 문장으로 정합니다.
그다음 핵심 주장, 수치, 인용, 버전 의존 설명을 목록화하고 각 항목을 1차 출처와 연결합니다.

공식 문서, 표준, 원 논문, 공식 API 문서를 우선합니다. 근거가 부족한 주장은 제거하거나, 불확실성과 적용 조건을 명시하거나, 글의 범위를 좁힙니다.

아티클 기반 글은 원문을 출발점으로만 사용합니다. 원문의 주장과 확인한 근거가 다르면, 원문의 맥락이나 버전을 밝힌 뒤 검증한 근거를 기준으로 설명합니다.

## 글 작성

검증을 마친 뒤에만 `src/content/blog/<category>/<slug>.md`를 만듭니다.

- 기존 공개 URL 또는 파일과 충돌하는지 먼저 확인하고, 충돌하면 덮어쓰지 않고 다른 적절한 슬러그를 선택합니다.
- 외부의 검증 가능한 기술 주장은 GFM 각주로 연결합니다.
- 아티클 기반 글은 frontmatter 바로 다음에 보이는 `> 원문: [원문 제목](원문 URL)` 블록을 넣습니다.
- 모든 신규 글은 본문 도입 전에 `## 핵심 요약`을 둡니다. 제목 아래에는 글의 판단과 독자가 얻을 결과를 1~3개의 짧은 서술형 문단으로 씁니다. 각 문단은 1~3문장으로 유지하고, `description`을 반복하거나 개조식으로 나열하지 않습니다.
- 주제 기반 글은 frontmatter 다음에, 아티클 기반 글은 원문 블록 다음에 핵심 요약을 둡니다. 그 뒤부터 일반 도입과 본문을 시작합니다.
- 실무 경험과 작성자의 판단은 외부 사실과 분리하고, 일반화하지 않으며 재현 조건이나 한계를 함께 씁니다.

## 검증과 인계

초안의 품질 게이트를 모두 통과한 뒤에만 인계합니다.
인계에는 초안 경로, 실행한 검사 결과, 주요 출처, 남은 확인 사항만 간결하게 적습니다.

사용자의 명시적 지시 없이 `draft`를 해제하거나, 커밋하거나, 푸시하지 않습니다.

## 중단 기준

다음 상황에서는 파일을 만들지 않고 사용자에게 필요한 맥락을 설명합니다.

- 핵심 주장을 뒷받침할 신뢰할 만한 근거가 부족한 경우
- 출처 간의 충돌을 적용 조건이나 버전으로 해소할 수 없는 경우
- 유효한 범위나 안전한 공개 경로를 정할 수 없는 경우
