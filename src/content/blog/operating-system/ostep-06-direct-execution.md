> 학습 자료: [OSTEP 6장 Mechanism: Limited Direct Execution](https://pages.cs.wisc.edu/~remzi/OSTEP/Korean/06-cpu-mechanisms.pdf)

운영체제는 프로그램을 직접 실행시키면 빠르지만, CPU 제어권을 완전히 넘기면 문제가 생깁니다. **Limited Direct Execution(LDE)** 은 사용자 프로그램을 하드웨어 위에서 직접 실행하되, 필요한 순간에는 운영체제가 제어권을 되찾도록 만드는 실행 모델입니다.

## 직접 실행의 장점과 한계

초기에는 운영체제가 사용자 프로그램의 명령을 하나씩 해석하고 수행하는 방식을 생각할 수 있습니다. 그러나 매 명령마다 운영체제가 개입하면 성능이 크게 떨어집니다. 직접 실행은 프로그램을 CPU에서 곧바로 실행하므로 빠릅니다.

문제는 두 가지입니다.

1. 사용자 프로그램이 디스크 I/O, 메모리 할당처럼 **특권이 필요한 작업**을 어떻게 요청할 것인가?
2. 프로그램이 CPU를 계속 점유할 때 운영체제가 어떻게 제어권을 되찾아 다른 프로그램을 실행할 것인가?

## 사용자 모드와 커널 모드

하드웨어는 보통 사용자 모드(user mode)와 커널 모드(kernel mode)를 구분합니다. 사용자 모드에서는 제한된 명령만 실행할 수 있고, I/O 장치 제어·인터럽트 설정·메모리 보호 변경 같은 특권 명령은 커널 모드에서만 가능합니다.

| 실행 모드 | 할 수 있는 일 |
| --- | --- |
| 사용자 모드 | 일반 계산, 사용자 주소 공간 접근, 허용된 명령 실행 |
| 커널 모드 | 특권 명령 실행, 장치 제어, 프로세스와 메모리 관리 |

이 구분 덕분에 응용 프로그램은 직접 실행의 성능을 얻으면서도 시스템 전체를 임의로 바꾸지 못합니다.

## System Call과 trap

사용자 프로그램이 파일을 열거나 프로세스를 만들려면 운영체제의 도움이 필요합니다. 이때 함수 호출만으로 커널 코드를 실행할 수는 없습니다. 대신 프로그램은 **system call**을 호출하고, 하드웨어의 `trap` 명령이 제어권을 커널로 안전하게 넘깁니다.

```text
사용자 프로그램
  ↓ system call
trap instruction
  ↓ 하드웨어가 레지스터와 PC를 저장하고 커널 모드로 전환
운영체제의 trap handler
  ↓ 작업 수행
return-from-trap
  ↓ 저장했던 상태를 복원
사용자 프로그램
```

trap table은 system call 번호나 예외 종류를 적절한 커널 handler와 연결합니다. 중요한 점은 사용자 프로그램이 trap table을 마음대로 바꿀 수 없다는 것입니다. 운영체제가 부팅 시 이를 설정하고, 하드웨어가 사용자 모드에서의 변경을 막습니다.

## 협력적 방식의 한계

운영체제가 제어권을 되찾는 가장 단순한 방법은 프로그램이 system call을 호출하거나 오류를 일으킬 때까지 기다리는 것입니다. 이를 협력적(cooperative) 방식이라고 볼 수 있습니다.

하지만 프로그램이 무한 루프에 빠지거나 의도적으로 운영체제 호출을 하지 않으면 CPU를 계속 점유할 수 있습니다. 운영체제는 사용자 프로그램의 자발성에만 의존할 수 없습니다.

## 타이머 인터럽트와 선점

하드웨어 타이머는 일정 시간이 지나면 인터럽트를 발생시킵니다. 인터럽트가 오면 CPU는 현재 사용자 프로그램의 실행을 멈추고 운영체제의 interrupt handler로 이동합니다. 운영체제는 이 시점에 현재 작업을 계속 실행할지, 다른 작업으로 바꿀지를 선택할 수 있습니다.

타이머는 운영체제가 아닌 하드웨어가 신호를 발생시킨다는 점이 핵심입니다. 그렇지 않으면 실행 중인 프로그램이 운영체제에 돌아갈 기회를 주지 않을 수 있습니다. 운영체제는 부팅 시 타이머를 설정하고, 사용자 프로그램이 이를 해제하지 못하도록 보호합니다.

## 문맥 교환

인터럽트나 system call로 커널에 진입한 뒤 스케줄러가 다른 프로세스를 선택하면 **context switch**가 일어납니다. 운영체제는 현재 프로세스의 레지스터, 프로그램 카운터, 스택 포인터 등 실행 상태를 PCB 같은 자료구조에 저장하고, 다음 프로세스의 상태를 복원합니다.

```text
Process A 실행
  ↓ timer interrupt
커널: A의 레지스터와 PC 저장
  ↓ scheduler
커널: Process B 선택
  ↓ B의 레지스터와 PC 복원
Process B 실행
```

문맥 교환 자체는 실행 정책(policy)이 아니라 실행을 가능하게 하는 **기제(mechanism)** 입니다. 어떤 프로세스를 고를지는 다음 장의 CPU 스케줄링 정책이 결정하고, trap·interrupt·context switch는 그 결정을 실제로 수행하게 합니다.

## 정리

- 직접 실행은 사용자 프로그램을 CPU에서 바로 실행해 성능을 얻습니다.
- 사용자 모드와 커널 모드가 특권 명령을 분리합니다.
- system call의 trap은 프로그램이 운영체제 서비스를 안전하게 요청하는 통로입니다.
- 타이머 인터럽트는 비협력적 프로그램에서도 운영체제가 CPU 제어권을 되찾게 합니다.
- 문맥 교환은 정책이 선택한 다음 프로세스로 CPU를 넘기는 기제입니다.
