> 학습 자료: [OSTEP 8장 Multi-level Feedback Queue](https://pages.cs.wisc.edu/~remzi/OSTEP/Korean/08-sched-mlfq.pdf)

SJF나 STCF는 작업의 실행 시간을 알아야 평균 반환 시간을 잘 줄일 수 있습니다. 실제 운영체제는 미래의 실행 시간을 알 수 없으므로, **Multi-level Feedback Queue(MLFQ)** 는 작업이 과거에 CPU를 어떻게 사용했는지를 관찰해 우선순위를 추정합니다.

## MLFQ가 풀려는 문제

대화형 작업은 짧게 CPU를 사용하고 I/O를 기다리는 일이 많습니다. 반면 계산 중심 작업은 CPU를 오래 사용합니다. MLFQ는 짧고 반응성이 중요한 작업에는 높은 우선순위를, CPU를 오래 쓰는 작업에는 낮은 우선순위를 주어 응답 시간과 공정성 사이의 균형을 맞추려 합니다.

| 목표 | MLFQ의 접근 |
| --- | --- |
| 응답 시간 | 높은 우선순위 큐를 먼저 실행합니다. |
| 반환 시간 | 짧게 끝나는 작업이 높은 우선순위에서 빨리 완료될 수 있습니다. |
| 공정성 | 같은 우선순위에서는 Round Robin으로 실행합니다. |
| 작업 길이 추정 | 미래를 직접 알지 못하므로 과거 CPU 사용 패턴을 피드백으로 사용합니다. |

## 기본 규칙

MLFQ에는 여러 우선순위 큐가 있고, 숫자가 낮을수록 높은 우선순위라고 가정할 수 있습니다. 기본 규칙은 다음과 같습니다.

1. 우선순위가 높은 작업을 먼저 실행합니다.
2. 같은 우선순위의 작업은 Round Robin으로 실행합니다.
3. 새 작업은 가장 높은 우선순위에 둡니다.
4. 작업이 자신의 time slice를 모두 사용하면 한 단계 낮은 우선순위로 내립니다.

![여러 우선순위 큐와 작업의 강등을 설명하는 MLFQ 기본 구조](/images/ostep/mlfq-basic.png)

_그림 11.1. 높은 우선순위 큐가 비어 있을 때만 낮은 우선순위 작업이 실행됩니다. 출처: OSTEP 8장_

새 작업을 높은 우선순위에 두는 이유는 간단합니다. 막 시작한 작업이 짧은 대화형 작업인지, 오래 실행될 계산 작업인지는 아직 알 수 없기 때문입니다. 먼저 빠르게 실행할 기회를 주고, CPU를 계속 사용하면 그 행동을 근거로 우선순위를 낮춥니다.

## 기아와 priority boost

이 규칙만으로는 낮은 우선순위 작업이 **기아(starvation)** 에 빠질 수 있습니다. 높은 우선순위의 대화형 작업이 계속 들어오면 CPU 중심 작업은 오랫동안 실행되지 못합니다. 또한 작업의 성격은 시간이 지나며 바뀔 수 있습니다.

이를 해결하기 위해 일정 시간 `S`마다 모든 작업을 최상위 우선순위로 올리는 **priority boost** 규칙을 추가합니다.

> 일정 시간 S가 지나면 시스템의 모든 작업을 최상위 큐로 이동합니다.

![priority boost로 낮은 우선순위 작업에도 다시 실행 기회를 주는 시간축](/images/ostep/mlfq-priority-boost.png)

_그림 11.5. 주기적으로 우선순위를 초기화하면 낮은 큐의 작업도 다시 기회를 얻습니다. 출처: OSTEP 8장_

`S`를 너무 짧게 잡으면 CPU 중심 작업이 자주 높은 우선순위를 얻어 대화형 작업의 응답성을 해칠 수 있고, 너무 길게 잡으면 기아 문제가 오래 지속됩니다. 시스템의 목표에 따라 조정해야 하는 값입니다.

## 게임을 하는 작업과 누적 allotment

초기 규칙은 작업이 time slice를 다 쓰기 직전에 I/O를 요청하면 우선순위가 내려가지 않는 문제를 가집니다. 악의적이거나 우연히 그런 패턴을 보이는 작업은 높은 우선순위를 계속 유지할 수 있습니다.

![time slice 종료 직전 I/O를 요청해 강등을 피하는 작업의 예](/images/ostep/mlfq-gaming-tolerance.png)

_그림 11.6. I/O를 이용해 우선순위 강등을 피하는 gaming 문제가 생길 수 있습니다. 출처: OSTEP 8장_

이를 막기 위해 같은 우선순위에서 사용한 CPU 시간을 누적합니다. I/O로 CPU를 양보하더라도 정해진 allotment를 모두 사용하면 우선순위를 낮춥니다. 즉, 한 번의 연속 실행이 아니라 **해당 우선순위에서 실제로 사용한 총 CPU 시간**을 기준으로 판단합니다.

## 큐마다 다른 time slice

모든 큐에 같은 time slice를 주는 대신, 높은 우선순위에는 짧은 time slice를, 낮은 우선순위에는 긴 time slice를 둘 수 있습니다. 높은 우선순위의 대화형 작업은 빠르게 순환해 응답성을 얻고, 낮은 우선순위의 CPU 중심 작업은 문맥 교환 부담을 줄이며 실행할 수 있습니다.

![높은 우선순위에는 짧고 낮은 우선순위에는 긴 time slice를 주는 구조](/images/ostep/mlfq-time-slices.png)

_그림 11.7. 우선순위별 time slice는 응답성과 문맥 교환 비용 사이의 절충입니다. 출처: OSTEP 8장_

## 정리

| 문제 | 보완 규칙 |
| --- | --- |
| 작업 길이를 모름 | 과거 CPU 사용을 피드백으로 우선순위를 추정합니다. |
| 낮은 큐의 기아 | 주기적인 priority boost를 사용합니다. |
| I/O로 강등 회피 | 우선순위별 CPU 사용 시간을 누적합니다. |
| 응답성과 오버헤드의 절충 | 높은 큐에는 짧고 낮은 큐에는 긴 time slice를 둡니다. |

- MLFQ는 작업의 미래가 아니라 **관찰된 행동**으로 정책을 결정합니다.
- 새 작업에는 높은 우선순위를 주되, CPU를 오래 사용하면 점차 낮은 큐로 이동시킵니다.
- 실제 정책은 priority boost, 누적 allotment, 우선순위별 time slice까지 갖춰야 기아와 게임 문제를 완화할 수 있습니다.
